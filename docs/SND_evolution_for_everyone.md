# Project SND 是怎麼一步步長成現在這樣的？（給非專業讀者）

## 這個專案在問什麼
先「封存」一個隨機特徵，之後再隨機決定一個測量角度。如果結果與角度之間有任何超出一般預期的關聯，就能量出來；沒有，就能嚴格說「上限是多少」。整份工作的重點不是證明神奇現象，而是**把「檢查」本身做到不會自欺**。

版本編號統一為三段：**V0.0.xx（機關期）、V1.0.xx（校對期）、V2.0.xx（轉向驗證期）**；前三個時期是想法階段，沒有版號。

## 一、異想期（無版號）：從一個大膽的念頭開始
一開始是形上學與量子干涉的猜想：未來的選擇會不會影響過去？
**學到的事**：這其實是量子「關聯」，不是能證明的「逆向因果」，而且沒有可以區分的預測。想法有趣，但不能檢驗。

## 二、摸索期（無版號）：找「歷史被改過」的指紋
接著嘗試各種物理模型，想找出可被量測的痕跡。
**學到的事**：大多數現象標準量子力學本來就允許，或違反「不可複製／不可傳訊」。所以必須換問法：不是證明奇蹟，而是「測不到時，上限有多低」。

## 三、建構期（無版號）：把問法變成統計問題
改用「相對熵、似然比、單側上限」，並估計需要約 10⁹ 筆資料。
**學到的事**：功效不夠、估計有偏差、常用定理的前提不成立、信賴區間覆蓋失效。需要更紮實的設計。

## 四、機關期 V0.0.01–V0.0.16：精巧但難以證明
這時期共 16 個版本，加上區塊子流形、平滑縮放、重要性加權、離散網格上限、次序統計量、去對齊自助法等機制。
**學到的事**：「公式寫得通」、「電腦算得出」、「錯誤率真的達標」是三件不同的事。機制越多，越難逐一證明。（各版細節多數沒有留下記錄，詳見 `CHANGELOG.md`。）

## 五、校對期 V1.0.01–V1.0.08：一份一份挑錯
共 8 份稿件，每一份都被逐點審閱，再據此改成下一份。
- 發現：樣本數估計約為 10¹⁰；「一維 Rice 界」比想像的保守得少；區塊內需隨機排列；置換須與實際分派一致。
- 其中一份（V1.0.07）反而退步，丟掉了先前的保護，之後被明確指出並回頭修補。
- 最後的 V1.0.08 被整個重寫。

## 六、轉向驗證期 V2.0.01–V2.0.13：用設計取代機制
核心換成兩件事：
1. **隨機化檢定**：因為角度是事後隨機抽的，檢定的錯誤率在數學上是精確的。
2. **一維上限（FC–Rice）**：把不確定性壓成一個數，有現成可驗證的表。

每一版都做模擬並寫稽核，標明哪些「已證明」、哪些「數值支持」、哪些「尚未驗證」。過程中多次更正自己，例如：
- 修正一個覆蓋率公式（ν/√κ 改成 ν/κ）。
- 找出一個會破壞保證的反例（區塊間漂移＋洩漏），誠實列為未解。
- 修正模擬程式自己的錯誤並重跑。

前一版（V2.0.08）處理最難的一類問題：如果「隨機抽角度」的機器暗中受到環境影響，而環境同時也影響資料，統計檢定就會被騙。這件事**資料本身無法證明不存在**。所以新版做三件事：把「被騙的程度」寫成一條可查的曲線；對「有裝感測器監測的環境因素」另做一個精確的檢查，檢查不過就不下結論；對沒有監測的部分，老實寫成「假設」，而不是「結果」。

V2.0.09 則修一個副作用：新增的「閘門」會讓少數正常結果被誤擋，使原本預留的資料量餘裕縮水，所以把需要的資料量上調約 9%（工期約多一個月），讓餘裕回到約一成。

V2.0.10 則回答一個一直懸著的設計問題：「隨機種子什麼時候取？」如果在收集資料之前就取好，角度其實早就決定了，資料就有機會（透過某條沒堵好的管道）事先知道角度；這樣即使看到「資料與角度有關」，也分不出是真的有奇怪的依賴，還是普通的洩漏，而且違背最初的實驗動機（角度要在資料封存之後才決定）。所以新版規定：全部資料收完並封存、拿到外部時間戳之後，才一次性取得種子，次數受限、全程留紀錄、不能追加資料重跑。同時新增一個數學結果：只要角度的唯一隨機來源就是這顆種子，那麼不論洩漏從哪條管道來，偏差大小都被「種子被動手腳的程度」限制住。這把原本「只能假設」的那一塊縮成兩件事：一個可以事後由別人重算來檢查的條件，和一個清楚的物理假設（隨機數產生器的輸出不能被環境或操作者操控）。後者仍然無法由資料證明。

V2.0.11 沒有改規範的內容：上傳到 GitHub 後發現公式顯示成殘缺的文字（公式的寫法 GitHub 不認得），所以把全部文件的公式改成 GitHub 看得懂的寫法，並用程式逐條檢查每個公式都能正確解析。同時整理了授權條款：程式碼是 MIT，規範、文件、結果與中繼資料是 CC BY 4.0，每個檔案都明確屬於其中一種，並由程式檢查沒有遺漏。

V2.0.12 同樣沒有改規範的內容：公式在 GitHub 上雖然看得到了，但有些符號排得怪，字母上的橫線變成飄浮的小點、帶波浪符號的量的平方被頂得太高。所以把這兩類寫法換成 GitHub 上顯示正常的樣子，意思完全一樣；帽子蓋在高字母上的位置是標準排版，沒有改。

V2.0.13 是第一次在 V2.0.10 之後再動規範內容。起因是一位 AI 審閱者建議「亂數要用明確傳遞的產生器，才能跨電腦、跨核心數得到完全一樣的結果」。檢查後發現：程式本來就不靠全域狀態，但規範上寫的亂數演算法（Philox4x32-10 或 Threefry）與程式實際用的（Philox4x64-10）不是同一個，而且「角度是怎麼從種子變出來的」只寫了概念，沒有寫到別人能逐位元重做的程度。所以新版把這件事寫成可以照著做的規格，附上已知答案的測試向量和一份只用整數運算的參考程式；重抽的每一次計算只取決於種子、區塊號和重抽序號，所以用幾顆核心、什麼順序都得到同樣的結果。另外也固定了求和的順序。電腦用的小數有捨入誤差，所以如果某次重抽的數值和觀測值近到誤差可能改變結論，新版不是直接放棄，而是先約定好一套不受電腦捨入影響的算法（只用整數，精確到好幾十位）：不換種子、不換資料，只把那幾個太接近的數字用精確算法重算一次，能分出大小就照結果裁決，精度加到上限仍分不出、而且會影響結論時，才老實報告「數值上不確定」。這個情況預期非常罕見（理想化估計約兩百萬分之一的分析會遇到），但規則必須在看到資料之前就定好。中心化後的數據也在抽種子之前封存並加上雜湊，讓所有人用的是同一份輸入。同一位審閱者的第二個建議（程式碼註解標出對應的規範章節）也採用了，並由程式自動檢查標註是否都對得上。統計方法與數字沒有改。

這一版同時更正上一版發布時的一個疏失：雜湊清單裡有一個檔案的雜湊是舊的。已發布的版本標記不能改，所以說明寫在更新紀錄裡，清單在後續版本修正，並新增了一個工具，在發布前檢查雜湊清單與檔案完全一致。

**目前版本：V2.0.13。**

## 還沒做完的事
隨機數產生器是否真的不受環境操控（物理假設，資料證明不了）、角度是否必須在採集期間實體施加（若是，新程序不適用）、更一般的條件傾斜、實際資料量下的行為、特徵強度是否夠大、GPU 實測、硬體的角度零點對齊、角度產生程序用另一種程式語言獨立重做一次（註冊前必須完成）。這些都在文件中標為未驗證。

## 這個專案能被信任的理由
不是因為它宣稱成功，而是因為每一個主張都寫明了證據等級，錯了就改，改了就留下紀錄。
